# Stock Market SIGKILL Recovery

Run **Actions > E2E - stock_market recovery > Run workflow** using
[e2e-stock-market-recovery.yml](../../../../.github/workflows/e2e-stock-market-recovery.yml).
The workflow is manual-only and runs on GitHub-hosted Linux runners. Select
`standard`, `adaptive`, or `both` (default). Each selected variant runs a clean
control followed by a SIGKILL trial against the same committed golden.
Push and merge the workflow into the default branch to make its dispatch form
available, then select the branch under test. Use matching server/plugin versions,
including the source-build and plugin overrides used by the performance tests.

## Fixed Recovery Workload

Recovery is deliberately separate from the throughput scenario. It preserves the
HTTP stock source, gRPC watchlist source, synthetic `WATCHES` join, and HTTP
reaction, but replaces the random model with two finite scripts generated by
[workload.py](workload.py):

- Three stocks, initial inserts plus 2,000 revisions: 6,003 HTTP input events.
- 64 watchlist entries per symbol, initial and terminal revisions followed by
  deletion of all NVDA entries: 448 gRPC input events.
- The query includes both source revisions and watchlist IDs. The final snapshot
  contains 128 full rows for MSFT and AAPL, including their final prices/volumes.
- The extra join fan-out creates pending query work for drain-phase injection.
- Standard and adaptive use identical scripts, timestamps, query, and golden.
  Adaptive batching is enabled on both dispatchers, with a 50 ms maximum wait.
- No 75% record-count cutoff and no stream SHA gate are used for recovery.

[golden.json](golden.json) is a versioned **analytical expectation**, not an
observed delivery capture. Its row templates expand to one row per watchlist ID.
Tests independently replay both scripts and check the complete golden row
multiset. Every run records the script hashes, event counts, golden hash, query
configuration, and workload fingerprint. Changes to the workload require review
and a new golden version, not copying a failing run's output over the expectation.

## Crash and Verification

1. Require RocksDB indexing, redb state store, persisted configuration, WALs on
   both sources (100,000 events each), and a 500,000-entry query outbox.
2. Start the observer explicitly before the two manual sources. Keep it alive
   throughout the crash; source scripts are not restarted or resent.
3. Wait for exact successful drain markers from **both** sources and confirm
   their `Finished` state. Markers are emitted only after dispatcher close
   succeeds. Failed drain and process exits fail the test.
4. Save the pre-crash snapshot. If it already equals the terminal golden, fail
   with `Drain window missed`; an already-completed workload must not count as
   successful drain-phase recovery. There remains a small observation-to-kill
   race; the snapshot records the last observed pending state, not an atomic
   query-progress barrier.
5. Send SIGKILL to the controller-owned server PID, verify signal termination,
   and restart the exact same binary/config against the same data directory.
   There is no component re-apply or bootstrap fallback.
6. Require the full terminal-revision snapshot before the timeout. Compare it
   through the existing Rust `recovery-compare` engine. Missing/extra rows,
   multiplicity or value differences, missing comparison data, a missed crash,
   and timeouts fail. Quiet output and mere server health never establish success.

The enforced scope is **recovered query snapshot equality for this bounded
workload**. It does not prove that every intermediate result was delivered, or
exactly-once/in-order HTTP delivery. `capture.complete` stays false and event
identities are absent; the comparator's overall/delivery verdict remains
inconclusive. The workflow explicitly checks the separate state verdict and
reports `delivery: not_verified`. It does not relax the shared comparator.

The clean run validates the server against the fixed golden; it never generates
or replaces the expectation used by the crash run. A missing/failed clean or
SIGKILL verdict fails the job. There is no schedule, Azure VM provisioning, or
publication to the performance history in this recovery workflow.

## Local Run

Prerequisites: Python 3, Ruby, matching Drasi Server plugins, and rebuilt framework
binaries. From the repository root:

```bash
cargo build --locked --manifest-path e2e-test-framework/Cargo.toml \
  -p test-service -p test-run-host --bin test-service --bin recovery-compare
export TEST_SERVICE_BIN="$PWD/e2e-test-framework/target/debug/test-service"
export RECOVERY_COMPARE_BIN="$PWD/e2e-test-framework/target/debug/recovery-compare"
export DRASI_SERVER_BIN=/absolute/path/to/drasi-server

python3 e2e-test-framework/examples/stock_market/recovery/run_recovery.py \
  --mode clean --variant standard --work-dir /tmp/stock-recovery-clean
python3 e2e-test-framework/examples/stock_market/recovery/run_recovery.py \
  --mode sigkill --variant standard --work-dir /tmp/stock-recovery-crash
```

Work directories must not already exist, preventing accidental reuse of persisted
state. Use `--variant adaptive` for both adaptive dispatchers. Add `--local-plugins`
only for trusted plugins already installed beside the server, to avoid replacing
them through registry auto-install. Otherwise registry/tag environment overrides
are supported as in the stock performance runner. Default ports are 8091 (admin),
63124 (test service), 9005 (HTTP source), 50061 (gRPC source), and 9006 (reaction);
each has a command-line override. Existing listeners are rejected, not killed.

Artifacts retain configs, input scripts, source drain states, binary hashes,
server/service logs, before/after snapshots, normalized baseline/actual files,
the comparator report, and `verdict.json`. Restart-to-health time is reported
separately; it is not query catch-up time. Cloud runs upload these for 14 days.

```bash
cargo test --locked --manifest-path e2e-test-framework/Cargo.toml \
  -p test-run-host --lib drain_barrier_waits_for_success_and_rejects_failure
```

using a local Drasi Server 0.2.2 build and matching plugins. A GitHub run with the
